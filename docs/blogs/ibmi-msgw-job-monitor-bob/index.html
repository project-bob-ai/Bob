The Use Case — MSGW Job Monitoring for L1 Operations

In most IBM i shops, experienced IBM i developers have no trouble handling MSGW jobs. They open WRKACTJOB, filter by status, and act. But production monitoring is increasingly shared with Level 1 service desk analysts — people who do not have an IBM i background.

When a batch job enters MSGW (Message Wait) status it has stopped. It is waiting for someone to reply to a system message. The existing process asked L1 analysts to scroll through hundreds of jobs in WRKACTJOB, spot the MSGW ones, and figure out what to do. That is not realistic for someone who was never trained on IBM i.

What they needed was a focused screen: only MSGW jobs, with labelled action options right there. No commands to know. Open it, see the problem, take action.

That is what I built — using Bob with IBM i Developer Mode (enabled through Premium Package for i (PPI)).

Code Generation

Bob generated two source members directly on the IBM i system through IBM i Developer Mode (enabled by Premium Package for i (PPI)):

  • BOB4IPGMR/QDSPFSRC(MSGWDSPF) — the DDS display file
  • BOB4IPGMR/QRPGLESRC(MSGWMON) — the SQLRPGLE program

The Display File — MSGWDSPF

The DDS had five record formats: MSGSFL (subfile), MSGCTL (subfile control), FOOTER (function key legend, lines 22–23), MSGQSFL and MSGQCTL (message subfile on line 24).

One detail in the subfile record stood out. IBM Bob added a hidden 28-character field SFQJOB to carry the full qualified job name — format number/user/name — on every subfile row. I had not asked for it. But it was the right engineering decision: CL commands like HLDJOB and ENDJOB require the fully qualified job name in number/user/name format. Storing it as a hidden subfile field means the RPGLE program reads it directly from the subfile record when the operator presses Enter — no string parsing, no lookup, no risk of assembling it incorrectly from individual parts.

The job count field is green when MSGW jobs are present and yellow when the list is empty. To make COLOR work, IBM Bob correctly defined CTJOBCNT as a named output field — the COLOR keyword in DDS is only valid on named fields, not on unnamed constants.

The RPGLE Program — MSGWMON

The SFILE(MSGSFL: WkRRN) keyword in the file declaration is essential — without it, the compiler does not recognise MSGSFL as a subfile format and READC, WRITE, and UPDATE on it fail. The ILE RPG — Free Format Skill from Premium Package for i (PPI) got this right.

The SQLRPGLE program MSGWMON uses an embedded SQL cursor to call QSYS2.ACTIVE_JOB_INFO() — an IBM i Service that returns a live snapshot of all active jobs on the system. The cursor filters with WHERE JOB_STATUS = 'MSGW' so only the jobs that need attention are returned. One technical detail IBM Bob handled correctly: JOB_NAME from ACTIVE_JOB_INFO is already the fully qualified name in number/user/name format — 327961/BOB4IPGMR/PGMA — not just the short job name. Bob used a nested LOCATE + SUBSTR expression to extract the short name for the display column, while storing the full qualified name in SFQJOB for use when building CL commands.

The Runtime Bug

This is where things got more interesting.

After the enhancements compiled, I pressed F5 to refresh and the function key legend on lines 22–23 had disappeared. Every refresh wiped it. I reported it to IBM Bob the way I would report a bug to a colleague:

"The function key footer disappears every time the subfile refreshes."

IBM i Developer Mode — drawing on the DDS diagnostic capability provided by Premium Package for i (PPI) — came back with a precise explanation:

"The root cause is that EXFMT MSGCTL performs a full-screen write. Without OVERLAY on the subfile control record, the 5250 data stream clears all screen positions not explicitly written by that operation — including the FOOTER record on lines 22–23. Adding OVERLAY to MSGCTL instructs the 5250 write to merge its output with the existing screen content rather than replacing it entirely."

Before — MSGCTL (missing OVERLAY)
     A          R MSGCTL      SFLCTL(MSGSFL)
-                            SFLSIZ(9999)
-                            SFLPAG(0015)
After — MSGCTL (OVERLAY added)
     A          R MSGCTL      SFLCTL(MSGSFL)
+                            OVERLAY
+                            SFLSIZ(9999)
+                            SFLPAG(0015)

One DDS keyword. IBM Bob caught it, explained the underlying 5250 write semantics, applied the fix, and after recompiling through IBM i Developer Mode the footer stayed on screen through every subsequent refresh.

The Bugs Bob Also Caught

The footer issue was the most visible problem. There were a few others. I want to be honest about them because they show how the collaboration with IBM Bob actually worked.

The Qualified Job Name Was Corrupt

Symptom: All CL commands — HLDJOB, ENDJOB, every option — were failing with "job not found" errors.

The root cause: JOB_NAME from QSYS2.ACTIVE_JOB_INFO() — accessed through the IBM i SQL Services provided by Premium Package for i (PPI) — already returns the fully qualified name in number/user/name format. The initial code was rebuilding it by concatenating JobNumber + '/' + JobUser + '/' + JobName. For a job like 327961/BOB4IPGMR/PGMA, the result was 327961/BOB4IPGMR/327961/BOB4 — double-encoded and truncated at 28 characters. Every CL command was failing with "job not found" or "matching parenthesis not found" because the closing ) fell past position 28 and got dropped.

Before — double-encoded
- SFQJOB = %trimr(JobRow.JobNumber) + '/'
-        + %trimr(JobRow.JobUser)   + '/'
-        + %trimr(JobRow.JobName);  // already full!
- SFJOBNAM = %char(JobRow.JobName); // showed nbr/usr/name
After — direct assign
+ SFQJOB   = %char(JobRow.JobName);      // '327961/BOB4IPGMR/PGMA'
+ SFJOBNAM = %char(JobRow.JobShortName); // 'PGMA' (for display only)

IBM Bob identified the issue from the error symptom, pointed to the ACTIVE_JOB_INFO column semantics that the IBM i Services knowledge in Premium Package for i (PPI) provided, and made the targeted fix. Nothing else changed.

The QCMDEXC Prototype Was Wrong

Symptom: Every QCMDEXC call failed with "String contains a character that is not valid" — even syntactically correct commands like WRKJOB JOB(327961/BOB4IPGMR/PGMA).

The initial prototype declared Cmd as varchar(32702) options(*varsize). When you pass a varchar variable to a varchar OPTIONS(*VARSIZE) parameter in ILE RPG, the compiler includes the internal 2-byte length prefix as part of the data stream. QCMDEXC receives those two bytes as the first characters of the command string — so WRKJOB JOB(...) arrived as '  WRKJOB J...' — two invisible leading characters — and the system responded with "character not valid".

Before — wrong
dcl-pr QCMDEXC extpgm('QCMDEXC');
-  Cmd    varchar(32702) options(*varsize) const;
   CmdLen packed(15:5)                   const;
end-pr;
After — correct
dcl-pr QCMDEXC extpgm('QCMDEXC');
+  Cmd    char(32702) options(*varsize) const;
   CmdLen packed(15:5)                 const;
end-pr;
Why this matters: The symptom gives you almost no information about where to look. You end up adding trace code, checking the command string character by character, eventually finding the ILE RPG calling-convention documentation carefully enough to notice the parameter type issue. The error analysis capability in IBM i Developer Mode in Premium Package for i (PPI) diagnosed this from the symptom description alone.

Option 5 Was Using the Wrong Command

Symptom: Option 5 (Display Messages) failed with "parameter not valid".

The initial implementation used WRKMSG JOB(...). The WRKMSG command takes a message queue object path — like WRKMSG MSGQ(QGPL/QSYSOPR) — not a job name. It does not accept a JOB() parameter. The correct command for viewing a job's inquiry messages is WRKJOB JOB(...) OPTION(*MSG). IBM Bob caught it and corrected it. A small thing, but an operator typing 5 and getting a command failure would have undermined trust in the screen.
